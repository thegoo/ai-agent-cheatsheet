⚡ Write once, use everywhere

Since tools read different filenames, use symlinks to keep a single source of truth. Most tools respect the nearest file in the directory tree.

# Write your instructions in AGENTS.md, then symlink for tool-specific filenames
ln -s AGENTS.md CLAUDE.md
ln -s AGENTS.md GEMINI.md

# Or start from CLAUDE.md if you're Claude Code-first
ln -s CLAUDE.md AGENTS.md

AGENTS.md
/ or any subdirectory

The open standard. A README for agents. Supported by Copilot, Codex, Gemini CLI, Cursor, Windsurf, Zed, and more. Most-nested file takes precedence. Plain Markdown — no required schema.

universal hierarchical open standard

// 04 — Orchestration Patterns

Orchestration Patterns

Three patterns cover almost every multi-agent use case. Pick the one that matches your task shape.

01
Fire and Forget
spawn → work independently → return summary
When to use
  • Parallel research or codebase exploration
  • Independent analysis tasks (security, quality, performance)
  • Batch operations across multiple files with no shared state
  • Tasks where verbose output would pollute the main context
Tools
Claude Code sub-agents Codex sub-agents Gemini CLI sub-agents
Key files
.claude/agents/*.md AGENTS.md
02
Coordinated Team
shared task list → agents observe each other → merge
When to use
  • Multi-file features spanning API, UI, and tests
  • Parallel implementation tracks that must eventually integrate
  • Work requiring specialist roles (frontend, backend, tester, reviewer)
  • Long-running projects where state needs to survive session close
Tools
Claude Code Agent Teams Squad on Copilot Cursor Mission Control
Key files
.claude/agents/*.md *.agent.md CLAUDE.md .squad/
03
Async Background
assign task → agent runs independently → delivers PR
When to use
  • Well-scoped GitHub issues with clear acceptance criteria
  • Routine work: test coverage, refactors, doc updates, bug fixes
  • Overnight or unattended execution on long tasks
  • Scheduled automations — issue triage, CI monitoring
Tools
Copilot Cloud Agent Codex Automations Cursor Background Agents Squad + @copilot
Key files
AGENTS.md copilot-instructions.md *.agent.md

⚡ Orchestration tips that actually matter

Parallel only when files don't overlap
The conflict isn't at runtime — it's at merge. Assign domain ownership explicitly before spawning agents.
Token cost multiplies linearly
5 parallel agents = ~5× token burn. Know your rate limits before running large teams. Use Haiku/Flash for research agents.
Sub-agents can't spawn sub-agents
Most tools default to max_depth=1. The orchestrator spawns workers; workers don't spawn more workers.
Always validate before merging
Parallel output needs a validation step — a dedicated reviewer agent or integration tests — before any merge.

// 06 — Tips & Pro Tips

Tips & Pro Tips

Basics for everyone. Advanced patterns for teams running real agentic workflows.

Basics
All levels
🪶 Keep it short
Every line in your memory file competes with actual work for context window. Target under 300 lines for CLAUDE.md, under 200 for AGENTS.md root before splitting into subdirectory files. Agents that run out of context mid-task produce worse output than agents with no instructions at all.
🔗 Point, don't paste
Reference other files instead of inlining content. Keep task-specific docs in agent_docs/ or docs/ and list them in your root file. Agents read what's relevant; unused context is wasted tokens. Use the @filename import syntax in CLAUDE.md to pull in other files on demand.
🚫 Never use for code style
Don't put linting rules or formatting preferences in instruction files. Use ESLint, Prettier, Black, or your formatter. LLMs are slow and expensive compared to deterministic tools. Reserve instructions for what only a human can explain — architecture decisions, domain context, non-obvious constraints.
⚡ Commands, not descriptions
Write the exact command (pnpm test --run --no-color), not a description of what it does. Include flags. Agents use these literally — vague wording causes hallucinated flags or wrong tool invocations.
📁 Use hierarchy for monorepos
Place additional AGENTS.md files in subdirectories. The nearest file in the directory tree wins. OpenAI's own repo uses 88 AGENTS.md files. Don't try to cover everything from the root — put frontend rules near frontend code, backend rules near backend code.
🔄 Treat it like code
Update instruction files in the same PR as the process change. Review them in code review. Audit quarterly. Outdated instructions actively hurt agent performance — worse than no instructions at all.
🧱 Set clear boundaries
Tell agents what NOT to do as explicitly as what to do. Include a "never do" section. Tell agents when to ask for human review rather than proceeding. Agents that know their limits are more reliable than agents with open-ended permission.
🔑 Never commit secrets
These files go into your system prompt and are version-controlled. Never include API keys, passwords, connection strings, or security vulnerability details. Treat the file as public documentation — because it effectively is.
Pro Tips
Advanced
⚙️ Use CLAUDE.md routing rules to force parallelism
Claude Code is conservative about spawning sub-agents by default. Add explicit routing rules to CLAUDE.md to change that behavior — specify which task types should always parallelize, which must be sequential, and which should run in background.
## Sub-Agent Routing Rules **Parallel dispatch** (ALL must be true): - 3+ unrelated tasks or independent domains - No shared state between tasks - Clear file boundaries, no overlap **Sequential dispatch** (ANY triggers): - Tasks have dependencies (B needs output from A) - Shared files or state (merge conflict risk) - Unclear scope — understand before proceeding
🌲 Git worktrees for multi-agent safety
When running multiple CLI agents (Claude Code, Codex, Gemini CLI) on the same repo, use git worktrees to give each agent a physically isolated codebase on disk. Conflicts surface at merge time with full context — not as a live race condition that corrupts shared state mid-write.
# Each agent gets its own worktree git worktree add ../feature-auth -b agent/auth git worktree add ../feature-api -b agent/api # Agents write to different disk paths — zero runtime conflict # Coordinator merges branches sequentially when done
🎯 Tight synthesis prompts beat good sub-agents
The orchestrator's synthesis prompt matters more than the sub-agent definitions themselves. A sloppy "combine these findings" wastes the entire fan-out. A tight synthesis prompt turns fragmented parallel results into a single decision-ready brief. Four lines is enough — be specific about format, priority, and what to discard.
You received findings from [N] parallel agents. Synthesize into: 1) top 3 actionable findings ranked by impact, 2) conflicts or contradictions between agents, 3) one recommended next action. Discard redundant detail. Max 300 words.
💰 Route by model, not just by task
Research and exploration agents don't need your most capable model. Use Haiku or Flash for read-only sub-agents doing codebase exploration, analysis, or documentation. Reserve Sonnet/Opus/GPT-5 for agents that write or modify code. In Claude Code, set model: claude-haiku-4-5 in your sub-agent frontmatter. Can cut parallel session costs by 60–80%.
📋 GitHub Issues as agent working memory
Structure issues specifically for agent consumption: acceptance criteria as a checklist, explicit file scope, test commands to run, definition of done. Agents assigned well-structured issues produce PRs that pass review on the first attempt significantly more often than those assigned vague issues. Treat issue writing as prompt engineering.
🔍 Audit agent conversations before context compaction
For long-running Claude Code sessions, run a conversation audit before compaction kicks in. Use a lightweight model to scan the conversation log for decisions, constraints, and context the agent has accumulated — extract the important parts back into CLAUDE.md or a working notes file. Prevents losing hard-won session context at the worst moment.
🛡️ Validate parallel output before merging — always
Never auto-merge parallel agent output. Designate a validator agent (read-only, review-focused) or run your integration test suite as the merge gate. Agents working in parallel can produce individually correct but mutually incompatible changes. The validation step is where the cost of parallelism pays for itself.
📦 Use APM or symlinks for multi-tool repos
If your team uses more than one tool, don't maintain separate instruction files manually. Either use APM to compile from a single manifest, or use symlinks to keep one authoritative file and link tool-specific names to it. Diverged instruction files across tools are worse than no files — they give different agents contradictory context about the same repo.
